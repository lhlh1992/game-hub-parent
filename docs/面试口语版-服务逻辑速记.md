# 面试口语版：各服务逻辑速记（精简版）

> 目的：给面试官用的“口语化解释”，只讲核心链路。

---

## 项目总览（面试可直接口述）

这是一个实时对战交互平台的后端项目，定位是“多人在线 + 实时对局 + 聊天 + 会话治理”的一体化能力。整体拆成四个服务：网关服务统一入口做鉴权和路由；游戏服务负责房间和对局（建房、入房、准备、落子、认输、重开）；聊天服务负责大厅/房间/私聊消息与通知推送；用户服务负责用户、好友、通知和文件存储，并与 Keycloak 对接认证。核心流程是：用户登录拿令牌 → 网关鉴权 → 进入大厅建房/入房 → 长连接建连进行对局实时落子 → 状态落 Redis（缓存）并广播快照 → 断线可恢复；聊天和通知在对局中实时推送并支持持久化。项目以房间ID做房间隔离，状态机 + Redis 条件写保证并发正确，会话失效事件通过 Kafka（事件总线）解耦广播，整体可扩展到更多小游戏场景。

## 项目亮点与实现逻辑（口语版）

### 第一梯队（面试官能听懂的业务亮点）

1) **多人同局不乱（落子不冲突）**
- 业务目标：同一回合只能有一个落子生效，避免双写和乱局。
- 实现步骤：先校验房间阶段与轮到方；写入时带“期望步数+期望轮到方”做原子条件写；冲突失败则提示客户端拉快照重试。
- 结果：并发覆盖转化为可控冲突，最终状态统一收敛。
- 技术实现：状态机校验 + Redis 条件写（期望步数/轮到方）。

2) **断线/刷新后能回到原局**
- 业务目标：用户掉线/刷新后继续原局，不用重开。
- 实现步骤：入座时下发“座位密钥”，重连时先用密钥恢复身份；服务端提供全量快照（棋盘、回合、计时）让前端一次性恢复。
- 结果：客户端状态以服务端快照为准，恢复稳定且可重复。
- 技术实现：座位密钥绑定 + 全量快照恢复。

3) **回合倒计时可靠**
- 业务目标：超时判负准确，重启后不丢计时。
- 实现步骤：倒计时由服务端统一管理，每回合刷新截止时间并持久化到 Redis；重启后从 Redis 恢复继续计时；超时判定只在服务端触发。
- 结果：避免前端计时漂移与多端不一致。
- 技术实现：倒计时引擎 + Redis 持久化恢复。

4) **单设备登录与踢线**
- 业务目标：同账号只保留一个有效会话，旧连接不可继续操作。
- 实现步骤：登录会话和长连接会话统一注册到 Redis；新登录触发旧会话失效事件；网关与服务端对每次请求做二次校验。
- 结果：即使踢线通知丢失，旧会话也会被校验拦截。
- 技术实现：会话注册表 + 失效事件广播 + 请求二次校验。

### 第二梯队（有价值但要讲细一点）

5) **房间不串**
- 业务目标：消息与操作只在本房间生效，杜绝串房。
- 实现步骤：路由主题、Redis 键、业务校验全部绑定房间ID；服务端按用户ID校验是否为房间成员/座位；座位密钥仅用于恢复身份，不作为授权凭证。
- 结果：前端传错参数也无法写入其他房间。
- 技术实现：路由隔离 + 数据隔离 + 成员授权。

6) **聊天消息可靠**
- 业务目标：消息实时可见，历史可追溯，不重复入库。
- 实现步骤：消息实时推送同时落库（Redis 缓存 + PostgreSQL 持久化）；大厅/房间按主题广播；私聊点对点推送并带客户端操作ID做幂等。
- 结果：实时体验 + 可回放历史，且不会重复写入。
- 技术实现：实时推送 + 落库持久化 + 幂等写入。

## 1) 网关服务（Gateway）

一句话：**统一入口 + 鉴权 + 路由 + 长连接透传 + 限流**。

- 所有 HTTP/长连接请求先过网关校验令牌。
- 合法请求再转发到游戏/聊天/用户服务。
- WebSocket 做握手鉴权和令牌透传，避免匿名连接。
- 维护令牌黑名单与会话失效校验，支持踢线。

你可以说：
> “网关就是统一门禁，先验身份，再转发，WS 也在这里做鉴权。”

---

## 2) 游戏服务（游戏对局）

一句话：**房间 + 对局状态机 + 实时落子 + 重连恢复**。

- 玩家建房、入房、准备、开始游戏。
- 对局中落子走长连接，服务端做回合校验和并发条件写。
- 状态快照落 Redis，断线重连靠快照恢复。
- PVE 模式会调 AI，落子也走同一套校验。

你可以说：
> “游戏服务就是管房间和对局，核心是状态机+条件写，保证同回合只成功一次，掉线还能恢复。”

---

## 3) 聊天服务（聊天与通知）

一句话：**大厅/房间/私聊消息 + 消息持久化 + 长连接推送**。

- 大厅和房间聊天走长连接广播。
- 私聊先校验好友关系，再写库并点对点推送。
- 历史消息存 PostgreSQL，Redis 做缓存。

### 聊天表设计（面试可说版）

- **会话表（chat_session）**：定义一个会话，类型分大厅/房间/私聊。
- **成员表（chat_session_member）**：记录会话成员和未读/已读状态。
- **消息表（chat_message）**：存储消息内容、发送者、时间、客户端操作ID（幂等）。

### 聊天流程（大体逻辑）

- 大厅/房间聊天：先确认用户在会话内 → 写入消息表 → 广播到对应主题。
- 私聊：先校验好友关系 → 获取/创建私聊会话 → 写入消息表 → 点对点推送。

你可以说：
> “聊天是会话模型统一大厅/房间/私聊，三张表：会话、成员、消息。先校验再入库，实时推送，私聊用客户端操作ID做幂等。”

---

## 4) 用户服务（用户与社交）

一句话：**用户/好友/通知/头像 + Keycloak 对接**。

- 用户注册登录走 Keycloak，系统服务同步本地用户资料。
- 提供用户资料、好友申请、通知管理等接口。
- 头像/文件存 MinIO。

你可以说：
> “系统服务就是用户域，Keycloak 负责认证，系统服务负责资料、好友和通知。”

---

## 5) 公共库（通用能力）

一句话：**会话治理 + 事件广播 + 通用工具**。

- 会话公共库：统一登录会话与长连接会话注册表。
- 会话事件库：会话失效事件发布与消费。
- Web 通用库：统一接口返回、令牌解析、服务间鉴权透传。

你可以说：
> “公共库主要是会话治理和跨服务复用，避免每个服务重复造轮子。”
