# 如何保证不串房间与并发一致性（面试官视角完整版）

> 目标：用于回答“多人在线、实时系统如何保证并发安全、权限安全、消息可靠与可控流量”。

---

## 0. 面试先给结论（30 秒版）

我把这类系统拆成五条防线：
1) **隔离**：按 `roomId` 做路由、存储、权限、写入上下文隔离，防串房；
2) **并发控制**：房间状态机 + Redis CAS，保证同回合只成功一次写；
3) **权限与安全**：JWT 鉴权 + 房间成员授权，不把 `roomId` 当权限凭证；
4) **流量治理**：网关/WS 限流、房间级热点保护、失败快速返回；
5) **可靠性**：关键状态落 Redis，消息有持久化与重放/快照兜底，服务重启可恢复。

---

## 1. 如何保证“不串房间”

这是底线能力，我做了四道闸门：

### 1.1 路由隔离（WS Topic 按 roomId）
- 订阅与广播都绑定房间主题（例如 `/topic/room.{roomId}`）。
- 客户端只会收到自己订阅房间的数据，不会跨房广播。

### 1.2 数据隔离（Redis Key 按 roomId）
- 房间元数据、棋盘状态、座位绑定、回合锚点都按 `roomId` 分区存储。
- 任何房间读写都只访问本房间键空间。

### 1.3 授权隔离（成员身份校验）
- 即使知道 `roomId`，也必须通过“是否该房间成员/座位”校验。
- 非成员不能落子、认输、重开、踢人等。

### 1.4 写入隔离（服务端强校验）
- 每个写操作必须带 `roomId` 上下文，服务端再次校验用户与房间关系。
- 不信任前端传参，前端传错或伪造会被拒绝。

**结论**：路由、数据、授权、写入四层都以 `roomId` 为边界，能有效杜绝串房。

---

## 2. 如何保证并发安全（尤其是落子）

### 2.1 房间状态机（先保证“能不能做”）
- 房间有明确状态迁移：`WAITING -> PLAYING -> WAITING/END`。
- 操作前先验状态：不在合法阶段直接拒绝。

### 2.2 Redis CAS 原子条件更新（再保证“并发下谁生效”）
- 落子提交带 `expectedStep + expectedTurn`。
- 只有匹配当前状态才成功；并发下只会有一个请求提交成功。
- 失败请求返回冲突，客户端拉最新快照收敛。

### 2.3 终局边界保护
- 认输、超时、最后一手可能并发到达，必须校验“是否已终局”。
- 终局类操作设计为“允许重复请求，不允许重复生效”。

**结论**：状态机负责合法性，CAS负责并发唯一成功，终局幂等负责边界安全。

---

## 3. 如何保证权限安全（`roomId` 暴露是否安全）

`roomId` 可见本身不是漏洞，关键是不把它当权限凭证。

### 3.1 身份鉴权
- HTTP/WS 都先做 JWT 身份校验，确定 userId。

### 3.2 房间授权
- 操作时检查“该 userId 是否有该 roomId 的操作权限”。
- 权限粒度可细化到房主/玩家/观战者。

### 3.3 会话治理
- 单设备登录下，旧会话失效后即使连接还在，也会被后续校验拒绝。

**结论**：`roomId` 只是路由标识，不是授权令牌。授权由服务端基于身份+关系判断。

---

## 4. 如何限流与抗流量冲击

多人实时场景不做限流，一定会被热点房间打穿。

### 4.1 网关层限流
- 按用户/IP/接口做基础限流，防刷与突发洪峰。

### 4.2 WS 消息限频
- 对高频消息（落子、聊天）做单位时间阈值控制。
- 超限直接拒绝或降级，避免拖垮房间线程与 Redis。

### 4.3 房间级热点保护
- 对同一 `roomId` 的写入做保护（比如排队/快速失败策略）。
- 防止一个热点房间影响全局房间。

### 4.4 下游保护
- Redis/DB/Kafka 连接池与超时要设置上限，避免级联雪崩。

**结论**：限流不只是网关，必须做到“入口 + 消息 + 房间 + 下游”四层联动。

---

## 5. 如何保证消息不丢失/不乱序（按业务分层）

先明确：不同消息可靠性等级不同。

### 5.1 对局状态消息（高一致）
- 以服务端状态为准，客户端靠 SNAPSHOT 收敛。
- 即使瞬时 WS 消息丢失，重连后也能通过快照恢复。

### 5.2 聊天消息（可持久）
- 实时推送 + 持久化存储（Redis 缓存 + PostgreSQL 历史）。
- 私聊支持幂等（客户端操作 ID）避免重复入库。

### 5.3 事件消息（最终一致）
- 会话失效等事件走 Kafka，消费端按幂等处理。
- 接受“至少一次投递”，业务层保证重复消费不产生副作用。

**结论**：通过“快照兜底 + 持久化 + 幂等消费”实现可恢复的消息可靠性。

## 6. 哪里最容易出并发问题（面试加分点）

1) 同房间同回合并发落子（最高风险）
2) 认输/超时/最后一手并发触发终局
3) AI 延迟任务与玩家操作交错
4) 单设备登录的多端同时登录竞态
5) 私聊重复发送导致重复入库与未读计数偏差

你可以补一句：
> 我们的设计不是假设这些不会发生，而是默认一定会发生，然后用状态机、CAS、幂等和校验去兜住。

## 7. 面试可直接背的标准回答（60 秒）

这个项目的并发和一致性我按五层做：第一，按 roomId 做全链路隔离，路由、存储、权限、写入都在房间边界内，避免串房；第二，房间内用状态机约束操作合法性；第三，关键写入用 Redis CAS，保证同回合并发只会成功一次；第四，鉴权和授权分离，roomId 可见但不作为权限凭证，必须校验用户与房间关系；第五，做流量治理和可靠性兜底，网关与 WS 限流、热点房间保护、快照恢复与消息持久化，确保在高并发下系统可控、可恢复、可审计。
